## 7 · SCHEMA-FAIL — routed to Canopus

**Finding:** SCHEMA.md provides two reference implementations for `self_hash` computation that produce different results for the same payload:

- Python (`json.dumps(sort_keys=True, separators=(',', ':'), ensure_ascii=False).encode('utf-8')`): produces hash `e58e0b26…` for the TASK-14 payload.
- bash/jq (`jq -cS 'del(.hashes.self_hash)' | sha256sum`): produces hash `8e078c82…` for the same payload.

The difference is a trailing newline (0x0a) that `jq -cS` appends but Python `json.dumps` does not. SCHEMA.md says "no trailing newline" in the Python section, but the bash section pipes jq output (which includes the newline) directly to sha256sum.

`sign-work.sh` uses the jq path. All existing v2 signatures were produced with the trailing-newline form. A verifier following the Python reference will report INTEGRITY-FAIL on every correctly-signed payload.

**Severity:** SCHEMA-FAIL (documentation defect in SCHEMA.md; sign-work.sh itself is internally consistent).

**Fix options for Canopus:**
1. Add `| tr -d '\n'` to the bash reference: `jq -cS 'del(.hashes.self_hash)' "$payload_file" | tr -d '\n' | sha256sum | awk '{print $1}'`
2. Or: acknowledge the jq trailing-newline as the canonical form, remove the "no trailing newline" note from the Python section, and update the Python reference to strip the trailing newline before hashing.
3. Or: deprecate the Python reference entirely and make jq the single authoritative algorithm.

Either way: the two examples in SCHEMA.md must produce identical output for identical input.
